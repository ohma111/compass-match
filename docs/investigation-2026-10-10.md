## 0. 先に結論 (3行)

1. **「部屋番号で使用できない言葉」は原因を特定した。** チャットの検査が、直近3分の自分の発言をつなげて調べている。そのため「1234」のあとに「ok」と送るだけで止まる。さらに、本当の理由が連絡先の検出でも「使用できない言葉が含まれています」と表示している。ローカルの Postgres で再現した。
2. **「重い」の主な原因は、DB の性能不足と、1つの変化でページ全体を描き直す作り。** 中でもポーリングとチャットの重複が大きい。ポーリングは募集詳細にしかなく、マッチングの待機画面は存在しない。リアルタイム基盤の乗り換え (Durable Objects・VPS・WebRTC) は、今の使用量では必要ない。
3. **ログアウトの最有力は「端末内でも Cookie の保存先が別」。** アプリ内ブラウザ・ホーム画面に追加したアプリ・Safari はそれぞれ別の保存先を持つ。加えて、一般の方にも見える「Discord でログイン」を押すと、別アカウントに切り替わる。どちらもコードと仕様の上で確認した。リフレッシュトークンの失効は Auth のログを見ないと分からない。

### 2-2. 今の実装 (コードで確認)

変化を見つけると `router.refresh()` でページ全体を描き直す。ログイン中だと、1回につき Vercel の関数2回 (proxy + ページ) と DB 約10本 (`viewer_header`、募集、参加の行、部屋番号、連絡先、発言200件、ブロック2本など。`src/app/(site)/recruitments/[id]/page.tsx:46`) になる。

**チャット**: Broadcast の合図を受けて発言だけ読み直す (`ChatRoom.tsx:73`)。

### 2-3. 原因が特定できたか

結論 (コードで確認):
1. **チャット1件で、参加者全員のページが描き直される。** 監視の比較に「最新の発言の id」が入っている (`LobbyLineup.tsx:26`)。チャットは Broadcast で取り直し済みなのに、20秒以内に全員が `router.refresh` する。3人の部屋なら、発言1件で関数6回・DB 約30本が余分に動く。チャットが多い時間帯ほど効く。
2. **操作のたびに2回描き直している。** `ActionButton` などは、Server Action の `revalidatePath` で描き直したあと、さらに `router.refresh()` を呼ぶ (`ActionButton.tsx:41`、`JoinButton.tsx:71`、`RoomCodePanel.tsx:26` など)。
3. **ログイン中の閲覧は、すべての遷移で proxy が動き、キャッシュも効かない。** 一覧 (`listRecruitments`) は1人ずつ DB に問い合わせる。
4. **プッシュ送信のたびに notifications 全体を探している。** 操作のたびに `after()` で `notifications` を `pushed_at is null and created_at > 10分前` で UPDATE する (`src/lib/push/server.ts:71`)。この条件に合うインデックスがない。今は通知が7日分なので小さい。

推定:
- 混雑時の遅さの本体は、10/9 の記録どおり DB の計算資源。Nano のときは Auth のヘルスチェックまで止まっていた。10/10 の朝に Pro + Small へ上げたあとも CPU 97%。その時点の1位は Realtime の `list_changes` (postgres_changes)。チャットを Broadcast に変えたので、migration 21 が適用されていれば、この負荷は消えているはず。**適用の有無と、適用後の CPU は未確定。**

### 2-4. 規模の見積もり (コードからの計算)

ピークを「1時間に56件 × 平均3人 × 1時間」とすると、詳細を開いている参加者は同時に約170人。
- 直接の問い合わせ: 170人 × 4本 ÷ 20秒 ≒ **毎秒34本** (全員が画面を見て操作している最大の場合)
- Vercel: 未ログインの閲覧は1閲覧1回。ログイン中は proxy の分で1遷移2回。描き直しと操作の重複が上乗せされる。

### 2-5. 影響と緊急度
全利用者。**高** (混雑時に止まる)。

## 4. ログアウト・引き継ぎ

### 4-1. 内容
- 突然ログアウトされ、部屋に戻れない
- 引き継ぎコードを作っていない人が戻れない
- 引き継ぎコードを作る場所が分からない
- Discord 連携の方法が分からない

### 4-2. 今の実装 (コードで確認)

- ログインは Supabase の匿名アカウント。セッションはその端末のブラウザの Cookie (`sb-jjhnmqeukfrknujtkash-auth-token`) にだけある。
- proxy が GET のたびに Cookie を Set-Cookie で400日に書き直す (`src/proxy.ts:44`)。Safari ITP の7日制限への対策。
- 引き継ぎコードは、マイページの「別の端末でも使う」(`MeView.tsx:90`) で作る。スマホでは「通知」の下にある。
- 「Discord でログイン」は、ログイン画面 (`/transfer`) の下に**見出しも説明もなく**表示されている (`AuthViews.tsx:50`)。v11 で「運営者用」の見出しを外した。
- 一般の方の Discord は、連絡先の文字列 (VC ありの募集で必須) にすぎない。アカウントの連携機能はない。

### 4-3. 原因

結論 (コード・仕様で確認):
1. **Cookie の保存先が分かれる。** 次はそれぞれ別の保存先を持ち、互いに見えない。
   - X・Discord・LINE のアプリ内ブラウザ
   - Safari と、ホーム画面に追加したアプリ (iPhone でプッシュ通知を受けるには、ホーム画面への追加が必要)
   - Chrome と Safari、プライベートモード

   募集のリンクを Discord から開くと、普段の Safari とは別人になる。これは匿名ログインの仕様上、避けられない。
2. **「Discord でログイン」を押すと、別のアカウントに切り替わる。** 一般の方が連携のつもりで押すと、Discord 用の新しいアカウントができる (`auth/callback/route.ts:16` → `/welcome`)。それまでの匿名アカウントの Cookie は上書きされ、コードがなければ戻れない。
3. **障害中に「未ログイン」と表示され、新しいアカウントを作ってしまう経路がある。**
   - Auth が応答しないと、トークンの更新や公開鍵の取得に失敗する。すると `getClaims()` がエラーを返し、画面は未ログインとして描かれる (`src/lib/auth.ts:44`)。Cookie は残っている。
   - その画面で「プロフィールを作成」を押すと、`getUser()` の失敗を「未ログイン」と同じに扱い、`signInAnonymously()` を呼ぶ (`ProfileSheet.tsx:114`)。
   - この時点で Auth が戻っていれば、新しい匿名アカウントで Cookie が上書きされる。10/9 の Auth 停止と時期が重なる。

推定・未確定:
4. **リフレッシュトークンの再使用による失効。** サーバー (proxy) とブラウザ (Realtime 用のクライアント) の両方がトークンを更新する。同じトークンが再使用の猶予 (既定10秒) を過ぎて使われると、Supabase はセッションごと失効させる。そうなると auth-js は Cookie を消す (`GoTrueClient.js` の `_callRefreshToken`、400系のとき)。Auth Logs の `refresh_token_already_used` の件数で確かめられる。
5. ITP の7日制限: ブラウザ側の更新で書いた Cookie は7日で切れる。サーバーの書き直しは次に来たときに効くので、7日以上来なかった方は消える場合がある。**実機では未確認** (CLAUDE.md の既知の弱点)。
6. 60日操作なしの自動削除は「突然」ではないので、今回の原因からは外す。

### 4-4. 影響と緊急度
匿名の利用者全員。失ったアカウントは戻せない。**高。**

### 4-5. 対策

| # | 内容 | 分類 | 実装 |
| --- | --- | --- | --- |
| A | 「Discord でログイン」を一般の画面から外す (`/transfer?admin=1` などにだけ出す)。または「運営者用。押すと別のアカウントになります」と明記する | 無料 | 小 |
| B | `ProfileSheet` の新規作成を、`AuthSessionMissingError` のときだけにする。通信エラーなら作らずに「混み合っています」を出す | 無料 | 小 |
| C | 未ログインと表示するのは Cookie がないときだけにする。Cookie があるのに検証に失敗したら「接続できません。再読み込み」の画面を出す | 無料 | 小〜中 |
| D | 参加・募集の直後に「引き継ぎコードを作る」への短い導線を出す (1回だけ)。マイページでは「別の端末でも使う」を通知より上に移す | 無料 | 小 |
| E | アプリ内ブラウザを判定し (UA の Line/Discord/Twitter/Instagram)、「Safari / Chrome で開く」帯を出す | 無料 | 小 |
| F | ブラウザ側のトークン自動更新を止め、更新はサーバーだけにする。チャットの Realtime には、サーバーから受け取ったトークンを `realtime.setAuth` で渡す。4 の競合をなくせる | 無料 | 中 |
| G | Discord を本人確認つきの引き継ぎ手段にする (`linkIdentity` で匿名アカウントに Discord をつなぐ)。Supabase の「Manual linking」の設定が必要 | 無料 | 中 |

## 5. 部屋番号・募集・参加

### 5-1. 「部屋番号を入れると『使用できない言葉』と出る」

**原因は特定した。** 部屋番号の欄ではなく、チャットで起きている。

- 部屋番号の欄 (`RoomCodePanel`) は、数字4桁以外を打てない。サーバーの返す文も「部屋番号は4桁の数字で入力してください」で、「使用できない言葉」は出ない (`actions/index.ts:207`、migration 13 の `set_room_code`)。
- チャットの DB トリガー `limit_chat` (migration 14) は、直近3分の自分の発言 (4件まで) と今回の発言を、**間を詰めてつなげて**検査する。中身は禁止語と連絡先の検出。
  - `normalize_for_filter` が記号・空白を消すので、数字同士・数字と英字がくっつく。
  - つなげた文で引っかかると、本当の理由に関係なく `'使用できない言葉が含まれています'` を返す (migration 14 の155行目付近)。
- 画面側 (`ChatRoom.tsx:93`) は今回の1件だけを調べるので、送信前には止まらない。

ローカルの Postgres 16 に migration 14 の関数を入れて確かめた結果 (banned = 禁止語の判定、contact = 連絡先の判定):

| 送った順 | つなげた文 | banned | contact | 結果 |
| --- | --- | --- | --- | --- |
| `1234` → `ok` | `1234ok` | f | **t** | 「使用できない言葉」 |
| `1234` → `5678` → `9012` | `123456789012` | **t** (10桁以上の数字) | f | 「使用できない言葉」 |
| `gg` → `1234` | `gg1234` | f | **t** | 「使用できない言葉」 |
| 1件で `1234 gg` / `s5 1234` / `room 2580` | | f | **t** | 「連絡先やIDは送信できません」 |
| `部屋1234` → `立て直し5678` → `3333` | | f | f | 通る |

部屋番号を貼ったあとに「ok」「gg」と返す、番号を何度か貼り直す、といった普通のやり取りで止まる。

影響: 参加者全員。部屋番号の連絡が止まる。**高。**

対策 (無料・小):
1. つなげて調べるのは禁止語だけにする。連絡先の検出 (英数字の混在・10桁の数字) はつなげない。または発言の間に区切りを入れる (`string_agg(body, ' ')`)。`normalize_for_filter` は空白も消すので、区切りは消えない文字 (例: `|`) にして、検査の前に分割する。
2. つなげた検査で止めたときの文を「分けて送った内容に、連絡先やIDに見える部分があります」にする。
3. 4桁の数字だけの発言は検査から外す (部屋番号として扱う)。
4. `tests/banned.test.ts` と `supabase/tests` に、上の表のケースを足す。

未確定: #コンパスの部屋番号が本当に4桁だけか (別のモードで桁数が違わないか)。運営者に確認したい。

### 5-2. 「部屋番号の更新に気づけない」

- 結論: 部屋番号を変えても通知は送らない (`notifications_kind_chk` に種類がない)。参加者の画面は、開いていて見えているときに最大20秒で変わる。変わったことを示す表示もない。
- ゲームのアプリにいる間は画面が見えていないので、監視は止まる。戻ったときに1回確かめて描き直すので、戻れば最新になる。ただし気づくきっかけがない。
- 対策 (無料・小〜中):
  - `room_code_changed` の通知とプッシュを足す (募集者以外の参加確定者へ)
  - 番号が変わったら数秒ほど朱で光らせ、「HH:MM に変更」と添える
  - 2章 F の Broadcast で即時に配る

### 5-3. 「コンパス側の固定部屋が落ちる」

**原因は特定できていない。** このサイトからゲームの部屋は操作できない。考えられる経路と確かめ方:

| 仮説 | 根拠 | 確かめ方 |
| --- | --- | --- |
| ゲームをバックグラウンドにすると部屋が解散する (ゲームの仕様) | 部屋番号やチャットを見るために、ゲームとブラウザを行き来する作りになっている | 実機で、カスタム部屋を作ってから Safari に切り替え、1・3・5分後に戻る。サイトを開かずにホーム画面へ出た場合と比べる |
| ブラウザの負荷で iOS がゲームを落とす | 募集詳細は時刻の表示を1秒ごとに更新している (`TimeRail`・`Countdown` の xl)。フォントも約500KB 読む | 同じ実験で、募集詳細と白紙のページを比べる |
| サイトの募集が60分で「終了」になり、部屋が落ちたように見える | 募集は全件60分固定。終わるとチャットが閉じ、マイページの「参加中」から消える | 報告者に、落ちたのがゲームの部屋かサイトの表示かを聞く |

対策 (確かめる前でもできるもの):
- 部屋番号とチャットを、ゲームに戻る前に一目で済むようにする (コピー1回で戻れる)
- 募集の延長 (5-4)

### 5-4. 募集の取り消し・参加の取り消し・部屋を閉じる

結論:
- どちらも RPC はある (`cancel_recruitment`・`cancel_participation`)。ボタンは**募集が有効な間 (開始から60分以内) だけ**出る (`RecruitmentDetailView.tsx:211`、`:293`)。
- 10/9 まではアプリ内ブラウザで `window.confirm` が出ず、押しても何も起きなかった (58f2a0c で修正済み)。報告がそれより前ならこれが原因。
- 「部屋を閉じる」(遊び終わり) のボタンはない。満員後の取り消し 82件 (1-1) は、閉じる代わりに「取り消す」を押していると考えられる。参加者には「参加予定の募集が取り消されました」が届き、意味が逆になる。
- 混雑で DB が止まっている間は、どの操作も失敗する (2章)。
- 4章でアカウントが替わると、自分の募集でなくなるので取り消せない (「募集者のみ取り消せます」)。

対策 (無料・小):
- 満員後 (または開始後) は「募集を締め切る / 遊び終わった」ボタンにし、status を ended に、通知は送らない
- 「延長する」(+30分、上限あり)
- 取り消しの失敗を画面に必ず出す (`ActionButton` は出しているので、`JoinButton` など他の経路を確かめる)

### 5-5. 「ブロックの影響で参加できない」

結論:
- 募集者とブロックの関係が (どちら向きでも) あると、参加は「この募集には申請できません」で拒否される (`request_join` の `is_blocked_between`)。ログイン中は、その募集が一覧からも消える (RLS)。
- **同じ文が「募集者に外された (rejected) 方の再参加」でも出る** (`request_join` 119行)。外された方は、ブロックされたと受け取る。
- 自分がブロックした方が参加者にいるときは、警告と確認が出る。席の「入る」は出ない (`LobbyLineup.tsx:139`)。仕様どおり。

対策 (無料・小): 外された方への文を「この募集には再度参加できません」に分ける。ブロックの理由は相手に知らせない今の方針のままでよい。
