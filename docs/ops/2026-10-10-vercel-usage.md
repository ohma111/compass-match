# 2026-10-10 Vercel の使用量の削減 (PR #7) と、その後の確認事項

リリースの翌日 (利用者 約1,300人) に、Vercel の無料枠の警告が2つ届いた。
- Function Invocations: 100万回のうち75%に到達 (運営者が受け取った警告メール)
- Fast Origin Transfer: 10GB のうち100%に到達 (同じく警告メール)

この文書の数字は、**実測したもの**と**推定・未確認のもの**を分けて書く。推定は推定と書く。

## 1. 変更内容と、本番で確認できた効果

### 原因 (本番で実測)
本番で未ログインのままホームを1回開いてスクロールすると、サーバーへのリクエストが42件あり、42件とも `x-vercel-cache: MISS` (関数が実行された) だった。うち41件が `<Link>` の自動先読み (`Next-Router-Prefetch`)。どのページも動的 (`force-dynamic`) で `loading.tsx` があるため、画面に入ったリンク (募集カード・タブ・フッター・絞り込み) ごとにサーバーで描画していた。表紙だけでも16件。
さらに proxy (`src/proxy.ts`) が、この1件ごとに動いていた。Vercel の料金ページでは Routing Middleware も Fluid compute の Invocation に数えると説明されている。この組織での実際の数え方は、ダッシュボードで未確認。

| キャッシュの HIT / MISS | Observability → Edge Requests | 共有画像と `/api/live` がキャッシュに当たっているか |

### 期間
- **反映前**:2026-10-09 05:38 UTC 〜 2026-10-10 05:38 UTC (反映の直前の24時間)
- **反映後**:2026-10-10 05:38 UTC 〜 2026-10-11 05:38 UTC (反映の直後の24時間)。曜日と時間帯の偏りを減らすため、できれば1週間後の同じ曜日の24時間とも比べる。

### 比べ方 (利用の増減で割る)
利用者がリリース直後から増え続けているので、合計の回数をそのまま比べると減り方を見誤る。どちらの期間についても、同じ「利用の量」で割った値を比べる。

## 3. 残っている最適化案 (実装はまだしない)

### A. 操作のあとの再読み込みの重複をなくす
- 今の動き:`ActionButton` は操作が成功すると `router.refresh()` を呼ぶ。操作 (Server Action) の中で `revalidatePath` をしていると、Next.js がその応答に更新後の画面を含めて返す (Next 16 のドキュメント `revalidatePath.md`:「Server Functions: Updates the UI immediately」)。そのため、続けて呼ぶ `router.refresh()` で、ページをもう1回サーバーで描いている。`JoinButton`(承認制の申請)・`RankSheet`・`ProfileSheet`・`AvatarPicker`・`RoomCodePanel`・`IntentRunner`・管理画面の `UserBulkForm` も同じ形。
- 期待できる効果:操作1回につき、関数1回とページ1枚分の Fast Origin Transfer が減る。全体に占める割合は、操作 (POST) の回数が分からないので未確定。
- 副作用:操作が今いるページを `revalidatePath` していない場合、画面が更新されなくなる。たとえば `setFollowAction` は `/me` と `/users/<id>` だけを更新する。`reportAction` と `feedbackAction` は何も更新しない。操作と、その操作が使われているページを1つずつ照らし合わせ、更新されることを確かめる必要がある。画面の見た目は変わらない。
- 作業量:中。対象ごとに確認が要る。

### B. 一度開いたページを30秒間使い回す (`staleTimes.dynamic`)
- 今の動き:動的なページは使い回さないので、タブを行き来するたびにサーバーで描く。
- 期待できる効果:30秒以内に戻ったページは読み込まない。下部タブで行き来する使い方が多ければ効く。
- 副作用:一覧の人数・通知の未読数・募集詳細が最大30秒古く見える。満員になった募集で「参加する」を押すと、DB が止めてエラーになる (データは壊れない)。操作で `revalidatePath` したページは使い回しが消えるので、自分の操作の結果は反映される。**利用者に見える変化があるので、入れるなら開発用プレビューで見てもらってから。**
- 作業量:小 (`next.config.ts` に1行)。

### C. 未ログインの方の募集詳細の自動確認を減らす (`/api/live`)
- 今の動き:参加していない方は45秒ごとに `/api/live/<募集ID>` を読む。CDN に10秒置くので、何人見ていても関数が動くのは1つの募集につき最大で10秒に1回 (本番で、2回目の取得が HIT になることを確認済み)。
- 期待できる効果:CDN に置く時間を10秒から30秒にすれば、1つの募集あたりの上限が1/3になる。間隔を45秒から延ばしても、同じ募集を見ている人が少ないとき以外はあまり変わらない。全体に占める割合は未確定。
- 副作用:見ているだけの方には、人数の変化の反映が最大30秒ほど遅れる。参加者・募集者は Supabase を直接読むので変わらない。
- 作業量:小。

### 提案する順番
1. **先に実測する** (2章)。ルートごとの内訳を見ないと、どれが効くか決められない。
2. 内訳で Server Action (POST) が多ければ **A**。見た目は変わらないが、確認の量は一番多い。
3. `/api/live` が多ければ **C**。変更は小さく、影響も小さい。
4. ページへの GET が多く、タブの行き来が多いと分かれば **B**。利用者に見える変化があるので、プレビューで見てもらってから。

## 5. 今残っているリスク (2026-10-10 時点)

### サイトが止まるリスク
- **Vercel**:Fast Origin Transfer は無料枠の100%に達したと警告が来ている。Hobby のままだと、プロジェクトが自動で止まり、多くの場合30日使えない (Vercel のドキュメント)。**Pro に上げたかは、この文書の時点で Claude は確認していない。** 上げていなければ、高い。上げていれば、使用量で止まるリスクはほぼない (Spend Management で「止める」設定にしている場合を除く)。
- **Supabase**:10/10 朝の時点で Pro + Small、CPU 97% (pg_stat_statements の1位は Realtime の list_changes)。チャットの Broadcast への切り替えは本番に入ったが、21 は未適用。今の CPU 使用率は**未確認**。アクセスが集中すると、DB が応答しなくなる (10/9 夜と同じ) おそれは残っている。
- **proxy の条件を絞ったこと**:本番の通しテストで、ログインが保たれることを確認した。Supabase のプロジェクトを変えるとビルドが止まる (仕組みとして入れた)。

### 予想外の課金のリスク
- Vercel Pro:基本料金20ドルに、20ドル分の利用分が含まれる。超えた分は使った量に応じて請求され、Spend Management の通知の初期値は200ドル。**30〜50ドルでの通知を設定したかは未確認。**
- Vercel の CDN リクエスト:Pro の定額に含まれるのは月100万件まで。JS・CSS・画像などの静的ファイルも数えるので、利用者の数によっては超える。超えたときの扱いと金額は、ダッシュボードで確認が必要。
- Active CPU:量が分からない。2章の数字が取れるまで、請求額の見込みは出せない。
- Supabase:Pro + Small の固定費のほかに、使った量に応じた分がある。Spend Cap の設定状態は未確認。

### データベースのリスク
- データが壊れる・消えるリスクは、今回の変更では増えていない (DB には触っていない)。
- バックアップ:Supabase Pro の毎日のバックアップがある。GitHub Actions の `db-backup.yml` は、Secrets に `SUPABASE_DB_URL` があるときだけ動く。**設定されているかは未確認。**
- 未適用の 17・19・20・21:流さないことでデータが壊れることはない。DB の負荷が下がらないことと、通報の証拠が残らないことが続く。
