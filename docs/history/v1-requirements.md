# #コンパス 遊び相手探しサービス 要件書 (MVP)

## 1. コンセプト
「#コンパスで、今この時間に一緒に遊べる人を見つけられるサービス」。
Discordの代替ではなく、Discordの外(ギルド外・サーバー未加入・XのFFでない人)とも遊び相手を見つける横断レイヤー。
運営は開発者1人。運営負荷を最小にする設計を最優先とする。

## 2. 前提と検証済みの事実(ユーザー申告)
- 開発・運営は1人。Xフォロワー約200人、協力的なギルド(約40人、管理者は協力的)あり。
- ギルド内では1日5〜6件の募集があり、約8割は埋まる。開始は21〜22時が多い。
- 想定: 登録者は最初の1か月で30〜50人。同時に動くのは10人前後。
- 課題: ギルド外の人へ届く入口(集客)。これは機能では解決しない。

## 3. 設計方針(重要)
1. **募集を主役にする。** 人数が少なくても価値が出るため。
2. **人数が少ない状態で「0人」を見せない。** 「今から遊べる」一覧は、閾値(設定値 NOW_LIST_MIN_USERS、初期30)を超えるまで人数を非表示にし、機能自体をフラグで隠せるようにする。
3. **DMは作らない。** チャットは募集ごとの部屋のみ。
4. **課金を前提にしない**が、後で追加できるDB構造にする(usersにplan列を持たせない。別テーブルで拡張可能に)。
5. **性別による絞り込み・性別募集は作らない。** 雰囲気タグで代替する。
6. **未成年保護:** 連絡先は承認後のみ開示。URL・画像はチャットで禁止。通報・ブロックを最初から搭載。
7. 公式素材(キャラ画像等)は使わない。文字とアイコンのみ。

## 4. MVP機能
### 4.1 認証
- Discordログイン、X(Twitter)ログインの2種(Supabase Auth)。
- 初回ログイン後にプロフィール作成へ誘導。利用規約・プライバシーポリシーへの同意必須。

### 4.2 プロフィール
項目: 表示名、ランク帯(選択式)、得意ロール(複数)、よく使うキャラ(自由入力・最大3)、目的(大会/ランク/エンジョイ/カスタム、複数)、VC可否、雰囲気タグ(初心者歓迎/まったり/ガチ/配慮してほしい 等、複数)、自己紹介(最大200字)、開示してよい連絡先(Discord ID / X ID / ゲーム内ID)。
- 連絡先は本人が選んだものだけ、募集の参加が承認された相手にのみ見える。
- 自己紹介はURL禁止。

### 4.3 募集
- 作成: タイトル、目的、開始日時、終了予定、募集人数、必要ランク帯(任意)、VC有無、雰囲気タグ、メモ。
- 表示: 一覧(今日・明日・目的別絞り込み)、残枠表示(現在2/3人)。
- 参加: 「参加したい」ボタンで申請 → 募集者が承認/拒否。承認で枠が埋まる。
- 状態: 募集中 / 満員 / 終了 / 取り消し。開始時刻+終了予定を過ぎたら自動で終了。
- 時刻はUTCで保存、表示はJST。

### 4.4 募集ごとのチャット
- 承認済み参加者と募集者のみが入れる、1募集1スレッド。1対1DMは作らない。
- テキストのみ。URLと画像は送信不可(サーバー側で検証)。1メッセージ最大300字。
- 「部屋番号」欄を別に持ち、承認済み参加者にのみ表示。
- 募集終了の一定時間後(初期6時間)にメッセージを自動削除。
- リアルタイム更新(Supabase Realtime)。連投制限あり。

### 4.5 今から遊べる(機能フラグ、初期はOFF)
- 「今から遊べる」ボタンで3時間後に自動消滅するステータスを登録。
- ONにすると一覧表示。人数が閾値未満なら人数は出さず「いま動いている人」を名前ベースで見せる。
- 初期リリースではフラグOFFで出荷し、コードだけ用意しておく。

### 4.6 通報・ブロック・BAN
- ブロック: 相手の募集が自分に見えず、相手は自分の募集に参加できない。
- 通報: 理由入力必須。対象はユーザー、募集、チャットメッセージ。
- 自動非表示: **異なる3人以上**(設定値)からの通報で、対象を自動で一時非表示にする(通報者の同一ID重複はカウントしない)。
- 恒久BANは管理者が通報理由を見て決める(管理画面)。
- 通報の悪用対策: 通報の多い通報者は重みを下げるための記録を残す(集計だけ、MVPでは自動処理しない)。

### 4.7 管理画面(管理者のみ)
- 通報一覧(理由・対象・件数)、ユーザーの停止/BAN/復活、募集の削除。
- フィードバック一覧。
- 管理者は roles で識別し、RLSで保護する。

### 4.8 フィードバック
- 常設のフィードバックフォーム(全ページのフッターから)。

## 5. 画面構成(スマホ優先)
1. トップ: 「今日の募集」(空でも寂しく見えない文言)、「募集する」ボタン
2. 募集一覧(日付・目的で絞り込み)
3. 募集詳細(参加ボタン、参加者、承認済みならチャット・部屋番号)
4. 募集作成
5. プロフィール編集 / 他ユーザーのプロフィール
6. 通知(承認・拒否・新着メッセージ)
7. 利用規約 / プライバシーポリシー / フィードバック
8. 管理画面
9. (フラグ)今から遊べる

## 6. データ設計(概略)
- profiles(id=auth.users.id, display_name, rank_band, roles[], characters[], purposes[], vc, tags[], bio, contact_discord, contact_x, contact_ingame, banned_at, created_at)
- user_roles(user_id, role)  ※管理者判定用
- recruitments(id, owner_id, title, purpose, starts_at, ends_at, capacity, min_rank, vc, tags[], note, room_code, status, hidden_at, created_at)
- participations(id, recruitment_id, user_id, status[pending/approved/rejected/cancelled], created_at) — (recruitment_id,user_id)ユニーク
- messages(id, recruitment_id, user_id, body, created_at, hidden_at)
- blocks(blocker_id, blocked_id)
- reports(id, reporter_id, target_type, target_id, reason, created_at) — (reporter_id,target_type,target_id)ユニーク
- feedback(id, user_id, body, created_at)
- presence_now(user_id, expires_at) — フラグOFFでも作成
- すべてRLS必須。連絡先・部屋番号は「承認済み参加者/募集者のみ」をRLSまたはRPC(security definer)で強制する。

## 7. 技術選定
- Next.js(App Router, TypeScript) + Tailwind CSS
- Supabase(Auth, Postgres, Realtime, RLS)
- ホスティング: Vercel(無料枠から)。PWA対応。
- 通知: MVPはアプリ内通知のみ。Web PushとDiscord DMは次フェーズ。
- Discord Bot連携(提携ギルドへの自動投稿)は**MVPには含めない**。設計上は recruitments からの投稿ができるよう拡張余地を残す。
- テスト: Vitest(ロジック)、可能ならPlaywright(主要フロー)。

## 8. セキュリティ・悪用対策
- 全テーブルRLS。フロントの制御に依存しない。
- 入力検証は共通スキーマ(zod)でサーバー側でも実施。URL・画像の禁止。
- レート制限(募集作成、参加申請、チャット、通報)。
- 環境変数・秘密鍵はコードに含めない。.env.exampleのみ。
- 個人情報最小化。ログにIDや連絡先を残さない。
- 年齢: 規約に「13歳未満の利用禁止・未成年は保護者同意」を明記。連絡先は承認後のみ開示。
- 法務: 性別募集を作らないことを前提とする。利用規約・プライバシーポリシーは雛形を用意し、公開前に本人が確認。

## 9. 検証指標(公開後2〜3週間)
- 合格ライン: 登録者30人以上 / ギルド外の人が参加した募集5件以上 / 実際に遊べた組3組以上
- 計測: 募集ごとの埋まるまでの時間、埋まらず終了した割合、ギルド外の参加回数(「ギルド外」の判定用に、募集の流入元パラメータ ?src= を保存)
- 届かなければ、機能追加ではなく入口(集客)の見直しを優先する。

## 10. 後回し(MVPに含めない)
日時カレンダー集計、お気に入り、フレンド、固定マッチング、雑談募集、性別絞り込み、課金、Discord Bot自動投稿、Web Push、1対1DM。
