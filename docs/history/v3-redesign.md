# v3 要件

v2 公開後の運営者フィードバック:
1. Discord/X 連携のアカウント登録は不要。プロフィールがあればよい。サイト内の ID・パスワードで完結させたい。
2. 「プロフィール登録したはずなのに、いろんな画面でまた登録させられる」不具合。
3. サイトデザインがまだ良くない。品質基準は Awwwards / Webby / FWA で受賞できる水準。

REDESIGN.md (v2) の内容は、ここで上書きしない限り有効。

## 1. 不具合(最優先・回帰テスト必須)
原因: `src/lib/auth.ts` と `src/app/users/[id]/page.tsx` が `profiles` を `select('*')` している。`profiles.signup_src` には authenticated の列権限がないため PostgREST が権限エラーを返し、エラーを「プロフィールなし」と扱って /welcome に戻している。
- 列を明示して select する。エラー時に「プロフィールなし」と誤判定しない(エラーはエラーとして扱う)。
- 他にも `select('*')` や列権限と食い違うクエリがないか全件確認。
- 回帰を防ぐテスト: db:verify の SQL テストに「authenticated で profiles の select('*') 相当は失敗する/アプリが使う列リストは成功する」を追加し、アプリが使う列リストを1か所の定数にしてテストから参照する。

## 2. 認証: ユーザーID + パスワード
- メイン: **ユーザーID(半角英数と _、3〜20字)+ パスワード(8字以上)** で登録・ログイン。メールは聞かない。
- 実装は Supabase Auth の email/password を使い、ユーザーIDから内部用の合成メールアドレスを作る。GoTrue のメール検証(形式・ドメイン・MX 等)を通り、かつ実在の誰かにメールが届かないドメインを選ぶこと。GoTrue のソース(github.com/supabase/auth)を確認して根拠を IMPLEMENTATION_NOTES に書く。自前でパスワードを保存・ハッシュしないこと。
- Supabase 側で必要な設定(Email プロバイダ有効、Confirm email OFF、など)を README に運営者手順として明記。
- ユーザーIDは profiles とは別に一意で保持(表示名とは別)。ログイン画面は「ユーザーID」「パスワード」の2欄。
- パスワードを忘れた場合の救済: 登録完了時に1回だけ「引き継ぎコード」(ランダム、ハッシュのみ保存)を表示し保存を促す。コード+ユーザーIDで新しいパスワードを設定できる。サーバー側で service_role を使う必要があるならその設計と、Vercel に追加する環境変数を README に書く(service_role は NEXT_PUBLIC_ を付けない、サーバー専用)。総当たり対策のレート制限を付ける。
- 登録フローは1画面: ユーザーID、パスワード、表示名、ランク帯、(任意)ロール、同意チェック → 「はじめる」。その場でログイン状態になり元の操作へ戻る。
- Discord ログインは「Discordでも入れる」の小さな副ボタンとして残す(既存の管理者アカウントが Discord のため)。X ログインは画面から外す。
- 悪用対策: 自動非表示の通報カウントは、作成から24時間以上経ったアカウントの通報のみ数える(DB 関数で)。登録のレート制限(同一IPの短時間大量登録)を入れられる範囲で入れる。

## 3. デザイン: 受賞水準
- /root/.claude/skills/frontend-design/SKILL.md を最初に読み、その手順(トークン設計 → 汎用デフォルトになっていないか見直し → 実装 → スクリーンショットで自己批評)に従う。
- 題材の世界観から視覚言語を作る: 3対3の対戦、カード、ロール(アタッカー/ガンナー/タンク/スプリンター)、試合前のマッチング画面の緊張感。公式素材・ロゴ・キャラは使わない。
- 避ける: 汎用 SaaS カードキット、黒背景+単一の蛍光色だけのダーク、全部同じ角丸カード、大文字トラッキングの見出しラベル、各セクションのフェードイン。v2 の黄色+紺の雰囲気からは明確に変えてよい。
- 動きは1か所に集中させる(例: 募集が満員になった瞬間、参加ボタンを押した瞬間の確定演出)。prefers-reduced-motion を尊重。
- 速度を落とさない: 募集は登録後3タップ以内、LCP を悪化させる重い演出はしない。
- 品質の最低ライン: 375px と 1440px で崩れない、キーボード操作とフォーカス表示、WCAG AA コントラスト、タップ領域44px以上。

## 4. 自己採点ループ(必須)
- 本番 Supabase に繋がず画面を確認できるプレビュー手段を用意する(例: 開発時のみ有効なフィクスチャデータ。本番ビルドでは無効になることをテストで保証)。
- Playwright(Chromium は /opt/pw-browsers に導入済み、`playwright install` はしない)で主要画面を 375x812 と 1440x900 で撮影: ホーム(募集あり/空)、募集作成、募集詳細(参加前/参加後・部屋番号/チャット)、登録、ログイン、マイページ。
- 撮影した画像を Read で見て、Awwwards の審査軸(Design / Usability / Creativity / Content)で各10点満点で採点し、具体的な欠点を列挙 → 直す → 再撮影。**全軸 8.0 以上になるまで繰り返す**(最大8周)。各周の点数と直したことを docs/design-review.md に記録する。
- 最終スクリーンショットを docs/screenshots/ に保存する。

## 5. DB
- 追加マイグレーションは1ファイル `supabase/migrations/20261001000006_v3.sql`。手で SQL Editor に貼るので、できるだけ小さく、seed なし、本番に1回流して安全なこと。2回流しても壊れないこと。
- 既存の RLS・連絡先の開示範囲・ブロック・レート制限は維持。

`npm run typecheck`、`npm test`、`npm run build`、`npm run db:verify` がすべて通る。README(運営者手順は v3 で必要になったものだけ、お金がかかる箇所に💰)と IMPLEMENTATION_NOTES(v3 節)を更新。main にコミット(push しない)。
